## 1. 色・画像以外に必要な変更

### A. 新規開発が必要なもの（3つだけ）

#### A-1. 【最重要】QR訪問でポイント獲得

MTGで「機能としてほぼ完成している」と共有したが、**実際にはコード上に該当機能はない**。近いものが2つあるが、どちらも転用できない。

| 既存の仕組み | 実体 | なぜ足りないか |
|---|---|---|
| `?cv=` キャンペーンコード<br>（`src/features/campaign-attribution/`） | サインアップ時の**流入元計測専用**。`user_campaign_attribution` に user_id × campaign_code を1行 INSERT。重複は先勝ちで無視 | ポイント付与が一切ない。1ユーザー1回だけ。**新規登録時にしか働かない**（既存ユーザーが会場QRを読んでも何も起きない） |
| `LINK_ACCESS` ミッション | ミッション詳細画面のボタンを押すだけで達成（`achieve-mission.ts:326` で成果物保存すらスキップ） | **QRを読まなくても達成できる**。URLを知っていれば自宅から取り放題 |
| `TEXT` ミッション（`artifact_label: 説明会で共有されたイベントコード`） | 入力テキストをそのまま保存するだけ | **サーバー側でコードを照合していない**。何を入れても達成 |

つまり「その場に行った人だけが達成できる」判定は**ゼロから作る必要がある**。

**実装方針（案）**

1. `src/lib/types/artifact-types.ts` に `VISIT_CODE`（仮）を追加
2. ミッションに秘密コードを持たせる
   - 案a: `missions` に `visit_code` カラム追加（1ミッション=1スポット。シンプル）
   - 案b: `mission_visit_codes` テーブル（1ミッションに複数コード。イベント日別に配りたい場合）
   - → **20スポット/10イベントの規模なら案a で十分**
3. QRの中身は `https://<domain>/missions/<slug>?k=<code>`
4. `src/app/missions/[slug]/page.tsx` でサーバー側照合 → 一致したら `achieve-mission` を呼ぶ
5. コードは `mission_data/missions.yaml` では管理しない（**公開リポジトリに秘密コードを置かない**）。別テーブル or 環境変数 or 非公開の同期スクリプト

**決めること**
- [ ] 同じスポットを何回も取れるか → `max_achievement_count` で制御可（`1` で1回、`null` で無制限）
- [ ] コードが SNS に流出したときどうするか（→ 「β版だから許して」でよい／コード再発行できる作りにしておく）
- [ ] 位置情報を併用するか → `IMAGE_WITH_GEOLOCATION` の仕組みが既にあるが、**QRだけのほうが運用が軽い**（推奨）

> 補足: 村井さんが指摘した「ポスターマップと近い」は的確。`map-posting` の「マップ上にスポットが並び、行くと埋まる」UI は周遊機能にそのまま転用できる。**だからポスター/ポスティングマップ系は削除ではなく非表示にすべき**（§2 参照）。

#### A-2. 公式LINE友だち追加を初回チュートリアルに

- **LINEログイン ≠ 公式アカウント友だち追加**。別物なので、ログインしただけではプッシュを送れない
- 現状のオンボーディングは `src/features/onboarding/constants/constants.ts` の `MOCK_MISSION` に「チームみらい公式サイトを見てみよう！」が**ハードコード**されている（HTML本文・アイコンパス込み）
- ここを「浜通りサークル公式LINEを友だち追加しよう」に差し替える
- 実ミッションとしても `mission_data/missions.yaml` に追加（既存の `add-supporter-line-friend` が雛形になる）
- 現状オンボーディングは navbar/Hero の「浜通りクエストとは？」ボタン起動のみ。**新規登録直後に自動起動する導線がない** → 追加が必要

#### A-3. 応募トークン発行

- マイページに「◯◯ポイント以上で応募できます」＋トークン表示
- トークンは `user_id` からの HMAC 等で生成し、Googleフォームの1問目に貼らせる（MTGでの合意どおり）
- 「自分のトークンを他人に渡す動機がない」ので流出耐性は十分
- 既存の `getUser()` + シーズンXP取得で必要な材料は揃っている。**小さい**

### B. 登録フロー（メアド廃止＋個人情報の最小化）

ここは「LINEボタンだけ残す」では終わらない。**登録直後に個人情報の入力を強制する導線が別に存在する**。

| 箇所 | 現状 | 対応 |
|---|---|---|
| `two-step-sign-up-form.tsx` | フェーズ2に「メールアドレスとパスワードで作成」ボタン | 削除 |
| `src/app/(auth-pages)/sign-up-email/` | メール登録ページ | 削除 or ルートごと除去 |
| `forgot-password` / `reset-password` | メール前提のパスワード再設定 | メアド廃止なら不要 |
| `two-step-sign-up-form.tsx:198` | **「浜通りクエストに登録することで、サポーターとしてチームみらいを応援することができます」** | **公開前に必ず修正**（事実と異なる。誤認リスク） |
| フェーズ1: 生年月日 + 18歳以上必須 | 公職選挙法（サポーター登録は18歳以上）由来 | **浜通りクエストでは根拠がない。要判断** |
| `private_users.date_of_birth` / `postcode` | DB上 **NOT NULL** | 消すならマイグレーションが必要 |
| `src/app/page.tsx:40` | プロフィール未登録なら `/settings/profile?new=true` へ**強制リダイレクト** | LINE登録直後に氏名・都道府県・郵便番号の入力画面が出る。「LINEだけで個人情報を持たない」方針と矛盾 |
| `public_user_profiles.address_prefecture` | NOT NULL | ただし**浜通りでは「訪問者の出身地」として価値あるデータ**。残す判断もあり |

**決めること**
- [ ] 生年月日を取るのをやめるか（やめる場合、DB NOT NULL 解除＋18歳チェック撤去）
- [ ] 郵便番号を取るのをやめるか（→ **やめるべき。個人情報管理体制の話に直結**）
- [ ] 都道府県は残すか（→ **残す推奨**。関係人口の可視化＝プロジェクトの目的そのもの）
- [ ] ニックネームだけ必須にして、登録直後の必須画面を1項目まで軽量化するか

## 2. 既存機能の削減方針

### 判断の原則

> **後で使いたくなりそうなら「非表示」、権利・審査・外部依存が絡むなら「削除」**

- 非表示は `is_hidden` / 導線を外す だけで済み、戻すのも一瞬
- 削除は他機能への依存を剥がす作業が発生する（下表の「巻き込み」列）
- ただし**外部APIの審査・キー・他人のアカウントに紐づくもの**は残しておく方がコストとリスクが高いので削除

### 機能別の判定

| 機能 | ファイル数 | MTGでの扱い | 判定 | 理由・巻き込み |
|---|---|---|---|---|
| `youtube` + `youtube-stats` | 42+16 | 「API審査が重い、外す」と明言 | **削除** | Google Developer 審査が必要。`metrics-index.tsx` / `missions/youtube-form.tsx` / `settings/youtube` / `auth/youtube-callback` / `api/[transport]` を巻き込む |
| `tiktok` + `tiktok-stats` | 26+15 | 同上 | **削除** | 同上。加えて `public/tiktok*.txt` は**他人のドメイン所有証明**なので即削除（チェックリスト P0-2） |
| `party-membership` | 16 | 言及なし | **削除** | チームみらい党員DB（HubSpot / Googleスプレッドシート）と実接続する機能。自前の会員制度は当面ない。巻き込み: `ranking-item.tsx`, `base-current-user-card.tsx`, `settings/profile/page.tsx`, `user-activity/timeline.ts`, `scripts/sync-party-memberships.ts` |
| `map-poster` | 40 | 「ポスターマップと近い」 | **非表示** | 選挙ポスター掲示板そのものは不要だが、**マップ×スポット×達成のUIは周遊機能で流用したい**。消すと作り直しになる |
| `map-poster-residential` | 18 | 同上 | **非表示** | 同上（優先度は低い） |
| `map-posting` | 35 | 同上 | **非表示** | 3つの中で最も周遊マップに近い（エリア分割＋達成記録）。**A-1 の実装で参考にする** |
| `prefecture-team` | 21 | 言及なし | **非表示** | 浜通り単独なので都道府県対抗は成立しない。ただし「訪問者の出身地分布」として再解釈する余地あり |
| `metrics`（donation / supporter / video） | 18 | 言及なし | **一部削除＋差し替え** | `donation-metric` は寄付、`supporter-metric` は外部API、`video-metric` は YouTube/TikTok依存。**「達成数」だけ残し、あとは「参加者数」「訪問スポット数」に差し替え** |
| `referral` | 2 | 言及なし | **残す** | 「友達を誘う」は浜通りでもそのまま有効。わずか2ファイル |
| `ranking` | 50 | デイリー＋全期間で現状維持 | **残す（一部非表示）** | 県別ランキング (`ranking-prefecture`, `get-prefectures-ranking`) だけ導線を外す |
| `user-level` / `user-badges` / `user-achievements` | 24/11/11 | ゲーミフィケーションは維持 | **残す** | ただしバッジ種別の `PREFECTURE` は無意味になる（`calculate-badges.ts:222`） |
| `onboarding` | 13 | チュートリアルとして活用 | **中身を差し替え** | §A-2 |
| `campaign-attribution` | 8 | — | **残す** | 「どの会場のQRから登録したか」の計測は浜通りでも普通に使える |
| `dev-tools` | 12 | — | **残す** | 自作。配色プリセットとページ一覧 |

### 非表示にする具体的な手段（既存の仕組み）

1. **ミッション単位** — `mission_data/missions.yaml` の `is_hidden: true`
   → 一覧から消え、詳細ページも404（`src/app/missions/[slug]/page.tsx:91,106`）。**データは残る。最も安全で可逆**
2. **カテゴリ単位** — `mission_data/category_links.yaml` から紐付けを外す
3. **ページへの導線** — `src/components/common/navbar.tsx`（ドロップダウンにマップ3種）、`src/app/footer.tsx`、`src/app/page.tsx` のセクション
   → **ルート自体は生きているので直リンクでは見える**。βでは実質これで十分
4. **完全に塞ぐ** — `src/app/xxx/page.tsx` を削除（`src/features/` は残す）。UI だけ消して実装は温存できる中間手段
5. **ホーム画面** — `src/app/page.tsx` のセクションを削除（`PrefectureTeamCard`, `MetricsWithSuspense` 等）。git履歴に残るのでコメントアウトは不要

> **注意**: `is_hidden` はミッション専用。カテゴリ・ページには同等のフラグがない。
> 機能フラグの仕組み（env による ON/OFF）はこのコードベースに**存在しない**。作るほどの規模ではないので、上記1〜5で運用するのが妥当。
