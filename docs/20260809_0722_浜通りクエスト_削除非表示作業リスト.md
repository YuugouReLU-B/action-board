### シーズン機能は「なくす」という選択肢がない

- **`achieve-mission.ts:293-299`** — `is_active: true` のシーズンが取れないと
  `"Current season not found"` で**ミッション達成が丸ごと失敗する**
- **`src/lib/services/seasons.ts:13`** — `.eq("is_active", true).single()`。
  active が **0本でも2本以上でもエラー**。常にちょうど1本必要
- `season_id` は `achievements` / `xp_transactions` / `user_levels` / `user_badges` の4テーブルに FK
  （カラムは nullable だが、書き込み側が必須扱い）
- ランキングのDB関数はすべて `p_season_id` 引数を取る（8本以上）
- アプリ側で `season_id` を参照しているファイルは **28本**

→ **「一旦シーズンの話はなし」は仕組みを残したまま実現する**。触るのは YAML の3行だけ。
そして MTG の「11月末で1回閉じて、来年またアップデートして帰ってくる」が**シーズン制度そのもの**なので、
後から必ず要る。**消さないのが正解**。

### 実施結果 ✅ 完了

- [x] `season_data/seasons.yaml` を **`season1` = 「2026 浜通りクエスト β」（2026-10-01〜2026-11-30, is_active: true）の1本だけ**に
- [x] 新規マイグレーション `20260809080000_reset_seasons_for_hamadori.sql` を追加
- [x] `supabase/seed.sql` / `supabase/seed-after-sync.sql` を単一シーズン構成に合わせて修正

**なぜマイグレーションが要ったか**

`seasons.yaml` を直すだけでは足りない。派生元のマイグレーション
（`20250811025829_create_season2.sql` / `20260209120000_start_season3.sql`）が
**新規DBでも season2 / season3 を作り、season3 を `is_active = true` にする**。
その状態で `season:sync`（upsert のみ・削除しない）を流すと
**`is_active` な行が2本**になり、`.single()` が壊れてミッション達成が失敗する。

マイグレーションの中身:
1. 全シーズンを `is_active = false` に倒す
2. 参照されていない `season2` / `season3` を削除（FK に `ON DELETE` がないため、
   実データがある環境では削除せず非アクティブのまま残す安全側の実装）
3. 削除できなかった場合に備えて選挙名だけ潰す
4. `season1` を浜通りβシーズンとして upsert し、唯一のアクティブにする

**seed.sql で追加対応が必要だったこと**

- `user_levels` の INSERT が**2ブロック**あり（旧 season1 用と旧 season3 用）、
  単一シーズン化で複合主キー `(user_id, season_id)` が衝突した → 過去シーズン側を削除
- 同じ理由で `user_badges` の「シーズン1のバッジ（過去シーズン）」ブロックも削除
  （`UNIQUE(user_id, badge_type, sub_type, season_id)` に抵触）
- `WHERE s.slug = 'season3'` を `'season1'` に統一（`seed-after-sync.sql` を含む）

### 注意点（ハマりどころ）

1. **`pnpm run season:sync` は upsert のみで、削除しない**（`season_data/src/sync.ts:67`）。
   YAML から消しても既存DBのレコードは残る。上記マイグレーションで対処済み
2. **slug をキーに upsert する**。改名すると別レコードとして新規作成され
   `is_active` が2本になる。**slug は `season1` から変えないこと**
3. **`end_date` は表示専用**。ミッション達成の可否判定には一切使われていない。
   11月末で閉じるのは **`is_active` を手動で false にする運用**
4. **`db reset` は必ず `pnpm run db:reset` を使うこと**（後述）
