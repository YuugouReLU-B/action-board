# LINE認証の監査と要件再定義

- 作成日: 2026-08-09
- 背景: 「認証周りに問題がないか確認したい。要件から考え直したい」
- 満たしたい要件（口頭）:
  - **最低ライン**: 各自が個人の LINE アカウントでログインする
  - **できれば**: そのログインと同時に公式LINEの友だち追加をする
  - **代替可**: 同時でなくてよく、初回クエスト「公式LINEと友だちになろう」の導線でもよい

**結論を先に**: その要件は LINE Login の標準機能でそのまま実現できる。しかも
「同時に追加」と「クエストで追加」は**排他ではなく、併用が最善**。
ただし着手前に、**本番で LINE ログインが確実に失敗する実装バグが1件**あるので先に潰す。

---

# 第1部: 現状実装の監査

## 全体のフロー

```
[ブラウザ] signInWithLine()                      src/features/auth/client/line-auth.ts
   state を localStorage に保存
   → https://access.line.me/oauth2/v2.1/authorize
        redirect_uri = window.location.origin + /api/auth/line-callback
        scope = profile openid email

[LINE] 認証・同意

[サーバー] GET /api/auth/line-callback           src/app/api/auth/line-callback/route.ts
   code と state をそのまま /auth/line-callback へ 302（NEXT_PUBLIC_APP_ORIGIN 基準）

[ブラウザ] /auth/line-callback                   src/app/auth/line-callback/page.tsx
   localStorage の state と照合（CSRF対策）
   localStorage から dateOfBirth を読む
   → handleLineAuthAction(code, dateOfBirth, ...) を呼ぶ

[サーバー] handleLineAuthAction                  src/app/actions.ts
   redirect_uri = headers().get("origin") + /api/auth/line-callback
   → lineLogin()                                src/features/auth/use-cases/line-login.ts
        LINE token エンドポイントで code を交換
        id_token を base64 デコードして sub / email / name / picture を取得
        get_user_by_line_id RPC で既存ユーザー検索
        無ければ auth.admin.createUser（user_metadata.line_user_id に保存）
        ランダムな一時パスワードを設定して返す
   → signInWithPassword(email, tempPassword) で Supabase セッションを張る
```

## 指摘事項

### 🔴 A. `redirect_uri` の生成元が3箇所でバラバラ — **本番で必ず壊れる**

| 場所 | 生成元 |
|---|---|
| `line-auth.ts:17`（authorize リクエスト） | `window.location.origin` |
| `api/auth/line-callback/route.ts`（302先） | `NEXT_PUBLIC_APP_ORIGIN` |
| `actions.ts`（token 交換） | `headers().get("origin")`、無ければ `http://localhost:3000` |

LINE は **authorize 時と token 交換時の `redirect_uri` の完全一致**を要求する。
つまり `window.location.origin` と `headers().get("origin")` が1文字でも違えば
token 交換が `invalid_grant` で失敗し、**ログインできない**。

これが揺れる現実的なケース:
- www あり / なし、独自ドメイン / `*.vercel.app` の両方でアクセスできる
- Vercel のプレビューデプロイ（毎回ホスト名が変わる）
- リバースプロキシ配下で `Origin` ヘッダが落ちる → `http://localhost:3000` にフォールバックして即死

**対応**: 3箇所すべてを `NEXT_PUBLIC_APP_ORIGIN` に一本化する。
LINE Developers 側のコールバックURL登録も同じ値にする。

> 現状ローカルでしか動かしていないため顕在化していないだけで、
> **ホスト版 Supabase / Vercel に載せた瞬間に踏む**。

### 🟠 B. `state` の検証がクライアント側だけ — ログインCSRF

`/auth/line-callback/page.tsx` は localStorage の `lineLoginState` と照合しているが、
その後に呼ぶ **`handleLineAuthAction(code, ...)` はサーバー側で state を一切見ていない**。

サーバーアクションを直接叩かれれば state 検証を素通りできる。
攻撃者が自分の `code` を被害者のブラウザで実行させると、
**被害者を攻撃者のアカウントでログインさせられる**（セッションフィクセーション）。

実害は「気づかず他人のアカウントで活動してしまう」程度でアカウント奪取ではないが、
正攻法は **state を HttpOnly cookie に置いてサーバー側で照合**すること。

同様に `dateOfBirth` も localStorage 経由でクライアント改ざん可能。
年齢は `lineAuthSchema` でサーバー再検証しているので**実害はない**が、cookie に寄せると一貫する。

### 🟠 C. リダイレクトが3ホップで不必要に複雑

`LINE → /api/auth/line-callback(server) → /auth/line-callback(client) → server action`

クライアントを経由している理由は **localStorage を読むためだけ**。
state と dateOfBirth を cookie に移せば **route handler 1本で完結**し、B も同時に解決する。
今は「ログイン処理中…」のスピナーが挟まる分 UX も悪い。

### 🟡 D. `scope=email` を要求している — 方針と矛盾

`line-auth.ts:33` が `scope=profile openid email` を要求している。

- LINE のメールアドレス取得は **LINE Developers での審査申請が必要**。未申請なら返ってこない
- MTG の方針は「個人情報を管理する体制が組み切れていないので LINE だけ」＝**メールは持たない方が良い**
- email が無ければ `line-{lineUserId}@line.local` という合成アドレスが入る（`line-login.ts:44`）。
  **これで全機能が問題なく動く**

**対応**: `scope` から `email` を外す。持たなくていい個人情報は要求しない。

### 🟡 E. ID トークンの署名・`aud`・`exp` を検証していない

`parseIdTokenPayload`（`src/lib/utils/jwt-utils.ts`）は base64 デコードするだけ。

ただしこの `id_token` は **LINE の token エンドポイントから TLS でサーバー直取得**しているため、
OIDC 的には署名検証の省略が許容される範囲（OIDC Core 3.1.3.7）。**現時点で実害はない。**

危険なのは、将来 id_token をクライアント経由で受け取る実装に変えた場合に
**無検証のまま任意のユーザーになりすませる**こと。
最低限そのことをコメントで残すか、`jose` で `aud` / `iss` / `exp` を検証しておく。

### 🟡 F. ログインのたびにパスワードを乱数で上書きしている

Supabase が LINE を OIDC プロバイダとしてサポートしていないための回避策。

`tempPassword` は **サーバーアクション内で完結していてクライアントには返っていない**ので、
漏洩はしていない（ここは実装として正しい）。
ただしログインのたびに `auth.admin.updateUserById` でパスワードを書き換えるのは無駄で、
`admin.generateLink({ type: 'magiclink' })` + `verifyOtp` の方が素直。優先度は低い。

### 🟡 G. 新規ユーザーは `/sign-in` から登録できない

`lineLogin` は `dateOfBirth` が無いと新規作成を拒否する（`line-login.ts:88`）。
つまり `/sign-in` の「LINEでログイン」を初見の人が押すと
**「新規ユーザー登録には各種同意と生年月日が必要です」で行き止まり**になる。

18歳制限（→ 未決事項）を外すなら、この分岐ごと消えて
**`/sign-in` だけで新規もログインも完結**する。導線が1本になるので検討価値がある。

# 第2部: 要件の再定義

## 使える標準機能: LINE Login の「友だち追加オプション」

**前提となる設定**

1. **Messaging API チャネル**（＝公式アカウント）と **LINEログインチャネル**を
   **同一プロバイダー**の下に作る
2. LINEログインチャネルの設定で「リンクされたLINE公式アカウント」に 1 を指定する

**これで使えるようになるもの**

| 機能 | 内容 |
|---|---|
| `bot_prompt` クエリパラメータ | authorize URL に付けると、認証フローの中で友だち追加を促せる |
| `bot_prompt=normal` | 同意画面に友だち追加のチェックボックスが出る |
| `bot_prompt=aggressive` | 同意後に友だち追加専用の画面が出る（取りこぼしが少ない） |
| token レスポンスの `friendship_status_changed` | その認証で友だちになったかが `true/false` で返る |
| `GET https://api.line.me/friendship/v1/status` | ユーザーのアクセストークンで叩くと `{"friendFlag": true/false}` |

> 実装時にパラメータ名と挙動は LINE 公式ドキュメントで再確認すること。
> 仕様変更の可能性があるため、ここの記述を鵜呑みにしない。

## これが要件に対して意味すること

**「ログインと同時に友だち追加」も「初回クエストで友だち追加」も両方できる。**
そして重要なのは、**`friendFlag` があるので友だち追加を自己申告ではなく実データで判定できる**こと。

現状のコードベースでは、この手のミッションは
`TEXT`（入力を検証せず保存するだけ）か `LINK_ACCESS`（ボタンを押すだけ）しかなく、
**どちらも「やっていなくても達成できる」**。友だち追加が自動判定できるのは大きい。

## 推奨要件

### 要件1: ログイン導線で友だち追加を促す（＝「最低ライン」＋α）

- authorize URL に `bot_prompt=aggressive` を付ける
- 実装は `line-auth.ts` に1行

### 要件2: 友だち状態をサーバーで判定して保持する

- token 交換の直後に `/friendship/v1/status` を叩き、結果を保存する
- **LINE のアクセストークンは保存しない**。30日有効な資格情報を持つとリスクだけ増える。
  保持するのは `line_friend: boolean` と評価時刻だけ
- 保存先は `user_metadata` か専用テーブル（後述の論点）

### 要件3:「公式LINEと友だちになろう」ミッションを自動判定にする

- 新しい artifact type（例: `LINE_FRIEND`）を追加
- ミッション画面のボタン → 公式アカウントの友だち追加URL（`https://lin.ee/xxx`）を開く
- 戻って「確認する」→ LINE 認証を1往復（同意済みなので無操作で戻る）→ `friendFlag` 再取得
- `true` なら達成、`false` なら「まだ友だち追加が確認できません」

### 要件4: これをチュートリアルの初回ミッションにする

- `src/features/onboarding/constants/constants.ts` の `MOCK_MISSION`
  （現在「チームみらい公式サイトを見てみよう！」がハードコード）を差し替え
- 新規登録直後にオンボーディングが自動起動する導線を追加（現状は手動起動のみ）

## なぜ「両方やる」のが最善か

- `bot_prompt` だけだと、**同意画面でスキップした人を後から拾えない**
- ミッションだけだと、**わざわざミッションを開かない人**を取りこぼす
- 両方あれば、ログイン時に大半が追加し、漏れた人はミッションで拾える。
  しかも `friendFlag` で判定するので、**すでに友だちの人はミッションを開いた瞬間に達成**にできる

# 第3部: 作業の優先順位

## P0 — β公開前に必須（要件2〜4の前提でもある）

1. **`redirect_uri` を `NEXT_PUBLIC_APP_ORIGIN` に統一**（指摘A）
   → これが直っていないと**本番で LINE ログインが動かない**
2. **`state` を HttpOnly cookie に移してサーバー側で検証**（指摘B）
   → 同時に3ホップを route handler 1本へ集約（指摘C）。まとめてやると効率が良い
3. **`scope` から `email` を外す**（指摘D）

## P1 — 要件の実現

4. `bot_prompt=aggressive` を付与（要件1）
5. `friendFlag` の取得と保存（要件2）
6. `LINE_FRIEND` ミッションの追加（要件3）
7. オンボーディング初回ミッションの差し替え（要件4）

## P2 — 借りの返済

8. `id_token` の `aud` / `iss` / `exp` 検証（指摘E）
9. `tempPassword` → `generateLink` + `verifyOtp`（指摘F）

# 決める必要があること

| # | 論点 | 補足 |
|---|---|---|
| 1 | `bot_prompt` は `normal` / `aggressive` どちらか | **`aggressive` 推奨**。MTG の「公式LINEから情報を届けたい」目的に対し取りこぼしが少ない。ただし同意画面の後にもう1画面挟まるので離脱は増える |
| 2 | 友だち解除されたら達成を取り消すか | **取り消さない推奨**（β。運用が複雑になる） |
| 3 | 友だち状態の再評価タイミング | ログインごと + ミッション画面の「確認する」で十分か |
| 4 | 友だち状態の保存先 | `user_metadata` は手軽だが検索性が低い。集計したいなら専用テーブル |
| 5 | 18歳制限を外すか（既出の未決事項） | 外すなら指摘G が解消し、`/sign-in` だけで新規登録まで完結できる |
| 6 | LINE チャネルの名義（既出の未決事項 1-b） | 開発中は個人プロバイダーでよい。**Messaging API チャネルと同一プロバイダーである必要がある**点が新たな制約 |

> **注意**: 要件2〜4 は「LINEログインチャネルと Messaging API チャネルが同一プロバイダーにあり、
> リンクされていること」が前提。**チャネルを作る段階でこの構成にしておかないと後で作り直しになる。**
> 論点6は「名義をどうするか」だけでなく「2つのチャネルをセットで作る」という設計判断でもある。
