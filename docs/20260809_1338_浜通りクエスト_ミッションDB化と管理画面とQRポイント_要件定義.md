# 浜通りクエスト ミッションDB化・管理画面・QRポイント取得 要件定義

作成: 2026-08-09
対象リリース: ベータ（2026-10-01 〜 11-30、ハマフェスは10/10）

---

## 1. 背景

MTG（2026-07-27）で「アクションをやった判定をどうするかに尽きる」と整理され、
**スポットやイベントに置いたQRを読むとポイントが入る**仕組みが最優先と決まった。
現状これは1行も実装されていない。

あわせて、この3つは分離できないことが分かったので1つの作業としてまとめる。

- **QRをミッションの1種別として設計する** — 達成記録・XP・ランキング・バッジ・
  シーズン・カテゴリ分けがそのまま乗る。別テーブルの「スポット」にすると全部作り直しになる
- **ミッションをDB正にする** — QRのシークレットは**公開リポジトリのyamlに置けない**。
  一方でシークレットだけDBに逃がすと1つのスポットが2箇所に分かれる
- **管理画面を作る** — DB正にすると編集手段が管理画面しかなくなる。DB化とセットで必要

### あわせて判明した設計上の問題

**ポイントはyamlに無い。** yamlにあるのは `difficulty`（1〜5）だけで、XPはコード側で
導出されている（`calculateMissionXp`）。

| difficulty | XP |
|---|---|
| 1 | 50 |
| 2 | 100 |
| 3 | 200 |
| 4 | 400 |
| 5 | 800 |

`is_featured` なら2倍。つまり**ミッションごとに任意のポイントを設定できない。**
「このスポットは遠いから300点」ができず、5段階のどれかに寄せるしかない。
MTGで「レベルデザイン的なものは検討が必要」と言われていた箇所でもあるので、
本作業で `points` 列を導入して解消する。

## 2. スコープ

### v1に入れる

- `missions` をDB正にする（`mission:sync` は初期投入専用に降格）
- `points` 列の新設（difficulty導出の廃止）
- 緯度経度の列（値は入れるが判定には使わない）
- QR種別の追加、シークレット発行、印刷用QR表示
- QR読み取りエンドポイント
- 管理画面: ミッションの一覧・作成・編集・表示ON/OFF

### v1に入れない

| 対象 | 理由 |
|---|---|
| カテゴリ・シーズン・クイズ設問の管理 | 数ヶ月に1回しか変わらない。yamlのままでよい |
| 達成の取り消し | 頻度が低い。当面SQLで対応（景品抽選前までに再検討） |
| 集計ダッシュボード | 後から足せる |
| 位置情報による不正判定 | 列だけ用意して判定はしない（§7参照） |
| POSTING系のポイント計算 | 浜通りでは使わない（全て非表示済み） |

## 3. データモデル

### 3-1. `missions` への追加

```sql
ALTER TABLE missions
  ADD COLUMN points integer NOT NULL DEFAULT 0,
  ADD COLUMN latitude  double precision,
  ADD COLUMN longitude double precision;

-- 既存データは現在の導出式で埋める（挙動を変えない）
UPDATE missions SET points = CASE difficulty
  WHEN 1 THEN 50 WHEN 2 THEN 100 WHEN 3 THEN 200
  WHEN 4 THEN 400 WHEN 5 THEN 800 ELSE 50 END;
```

`difficulty` は**残す**。★表示と難易度フィルタで使われているため。
以後 `difficulty` は見た目、`points` は実際のXP、と役割を分ける。

### 3-2. QRシークレットは別テーブルにする（重要）

`missions` の RLS は `select_all_missions` で**全員がSELECTできる**。
シークレットを同じ行に置くと **anon キーで全スポットのコードを一覧取得され、
現地に行かずに全ポイントを取得できる**。必ず別テーブルにする。

```sql
CREATE TABLE mission_qr_codes (
  mission_id uuid PRIMARY KEY REFERENCES missions(id) ON DELETE CASCADE,
  code       text NOT NULL UNIQUE,
  created_at timestamptz NOT NULL DEFAULT now()
);

ALTER TABLE mission_qr_codes ENABLE ROW LEVEL SECURITY;
-- ポリシーを一切作らない = service_role 以外はSELECTもできない
```

- `code` はサーバー側で生成（`randomBytes(16).toString("base64url")` 程度）
- **リポジトリには絶対にコミットしない**
- 再発行すると旧コードは無効になる（印刷物の刷り直しが要るので、UIで警告する）

### 3-3. 提出物の種別に QR を追加

`required_artifact_type` に `QR` を追加する。
既存の種別と違い**提出物が無い**ので、`mission_artifacts` には何も入れない
（`LINE_FRIEND` と同じ扱い）。

## 4. `mission:sync` の降格

現在 `.github/workflows/deploy.yml` の58行目でデプロイのたびに `mission:sync` が走り、
yaml の内容で DB を upsert している。**このままだと管理画面の編集が毎回消える。**

- `mission:sync` を **CIから外す**。手動実行のみにする
- yaml は「初期投入用の種データ」として残す（新環境構築時に1回流す）
- `season:sync` は**そのまま残す**（シーズンはyaml管理を継続するため）

> 補足: 現在 yaml 管理外のミッションが3件あり（`quiz-teammirai-beginner` など、
> 初期マイグレーションで直接INSERTされたもの）、これは先に yaml へ取り込み済み。

## 5. 管理画面

### 配置

`/admin` に置く。`/dev` は本番で404になる開発専用なので別にする。

- 認可は既存の `isAdmin()`（`app_metadata.roles` に `admin`）を使う
- **actions層で認可チェックを行う**。ページの404はURLを知られたら回避されるため
- 書き込みは Server Action + `createAdminClient()`

### 画面

| 画面 | 内容 |
|---|---|
| ミッション一覧 | タイトル / 種別 / ポイント / 表示ON-OFF / 達成数。種別と表示状態で絞り込み |
| ミッション編集 | タイトル・本文・アイコン・種別・ポイント・難易度・上限回数・注目・イベント日・緯度経度 |
| QR発行 | 種別がQRのときだけ表示。シークレット発行/再発行、QRプレビュー、印刷用ページ |

QRの描画は既存の `react-qr-code` を使う（`qr-code-display.tsx` の実績あり）。
印刷用ページはスポット名とQRを大きく並べただけのものでよい。

## 6. QR読み取りのフロー

QRが指すURL: `https://<origin>/q/<code>`

```
QRを読む
  ├ code が存在しない        → 「無効なコードです」
  ├ 未ログイン               → LINEログインへ（returnUrl=/q/<code>）
  │                             ログイン後に同じ処理へ戻る
  ├ 達成上限に到達済み       → 「このスポットは獲得済みです」＋ミッション詳細へ
  └ 未達成                   → 達成を記録してXP付与 → 完了画面
```

- 達成記録は既存の `achieveMission` を通す。XP・レベルアップ・バッジ・
  ランキングの更新をすべて再利用する
- スポットは `max_achievement_count: 1` を基本とする（1人1回）
- 未ログインからの復帰は、LINEログインの `returnUrl` 機構をそのまま使う
  （`line_login_return` クッキー）

## 7. 不正対策をどこまでやるか

**QRを写真に撮ってSNSに貼られたら、現地に行っていない人でも押せる。**
これはQR方式に本質的な弱点で、テーブル設計では解決しない。

| 段階 | 内容 | v1 |
|---|---|---|
| 1 | コード固定。対策なし | **採用** |
| 2 | 位置情報を併用し、スポットから半径N m以内のみ許可 | 見送り |
| 3 | 時間で変わるコード | 不採用 |

**v1は1を採用する。** ベータは「オープン検証」として期待値を下げて出す方針であり、
2を入れると屋内や電波の悪い場所で正当な利用者が弾かれるほうが痛い。
道の駅や個人商店に電子表示を置く3は現実的でない。

ただし**緯度経度の列は最初から持たせる**。2への移行と、周遊の可視化に要るため。

## 8. 既存コードへの影響

| 箇所 | 変更 |
|---|---|
| `calculateMissionXp(difficulty, isFeatured)` | `mission.points` を使う形に置き換え。呼び出しは `achieve-mission.ts` と表示側 |
| `achieve-mission.ts` | 取得カラムに `points` を追加。QR種別の分岐を追加 |
| `mission_data/src/sync.ts` | 初期投入専用であることを明示（既存レコードを上書きしない）|
| `.github/workflows/deploy.yml` | `mission:sync` のステップを削除 |

`is_featured` の2倍ボーナスは**v1では維持する**。ポイントを直接指定できるなら
冗長だが、既存のXPロジックを同時に変えると検証範囲が広がるため。

## 9. クラウドDBの扱い

ホスト版 Supabase（`hamadori-quest` / ref `kijylemmokeegoqxalny`）の現状:

- マイグレーションは develop の8/8時点まで
- シーズンが旧3件のまま。ミッションもデブランディング前（52件が表示中）
- テストの残骸 `dummy-slug-...` が1件混入
- **登録ユーザーは0人**

失うものが無いので、**本作業のマイグレーションが固まってから一度だけ作り直す。**
今の中途半端な状態に差分を当てるより手数が少なく、確実。

手順は別途整理するが、最低限これが要る。

1. `supabase link` してマイグレーションを全適用
2. `mission:sync` / `season:sync` を1回だけ手動実行
3. Vercel の環境変数をホスト版に向ける
4. LINE Developers のコールバックURLに本番URLを追加
5. `BASIC_AUTH_USER` / `BASIC_AUTH_PASSWORD` を Vercel に設定

## 10. 検証項目

- [ ] QRを読んで達成・XP付与・レベル反映まで通る

- [ ] 未ログインでQRを読み、LINEログイン後に達成まで戻る
- [ ] `mission_qr_codes` が anon キーで読めないこと（**必須**）
- [ ] 管理画面が非管理者から開けない。**サーバーアクションも直接叩けない**
- [ ] ポイントを編集すると以後の達成に反映される（過去分は変わらない）
- [ ] `mission:sync` を流しても管理画面の編集が消えない
- [ ] 印刷用QRが実機のカメラで読める
