# イベント参加分析データ基盤の要件定義

## 背景・目的

運営から次の分析ニーズが挙がった。

- どこから登録した人が
- 何個のイベントに行くか
- どのイベント → どのイベントか（遷移）
- 同じ日に複数イベントに行っているか

これらを継続的に集計できる状態にしておきたい。本ドキュメントは、現状のデータモデルを棚卸しした上で、何が既にあり・何が足りないかを整理し、対応方針を決めるためのもの。

## 結論（先に）

- 生データをBigQueryへ流す基盤（論理レプリケーション）は**既に存在する**。新規の集計自体はBQ側のSQL/dbtで完結でき、アプリ側に大きな新規実装は不要。
- ただし **LINE経由の登録情報（プロバイダ種別・友だち状態）が、社内公開用のBQパイプラインには乗っていない**。これは対応が必要（決定済み・下記参照）。
- **GEO_CHECKINミッションは `main` に既にマージ済み**（当初は `chore/hamadori-phase1-cleanup` ブランチのみで `develop` 未マージだったが、その後トランクを `main` に一本化し、GEO_CHECKIN機能もマージ済み）。Step 2のBQ側集計モデルは着手可能。
- 将来的に運営が直接見られる管理画面ダッシュボードも検討するが、まずはBQ側の基盤整備を優先する。

## 現状のデータモデル

### 「イベント」に該当する既存概念

このアプリで「ユーザーが物理的にイベントに行った」ことを表すのは、`missions` テーブルのうち `required_artifact_type` が `QR` または `GEO_CHECKIN` のもの。ユーザーが会場でQRを読む/位置情報チェックインすると `achievements` に1行できる。

| テーブル | 役割 |
|---|---|
| `missions` (`required_artifact_type IN ('QR','GEO_CHECKIN')`) | 1行 = 1つの物理イベント（会場）。`event_date`は**開催予定日**（実際の来場時刻ではない） |
| `mission_qr_codes` | QRミッションのコード |
| `achievements` (`user_id, mission_id, season_id, created_at`) | ユーザーが実際にそのイベントに来場した記録。`created_at`が**実来場時刻** |

> **同日判定・順序判定には `achievements.created_at` を使う**（`missions.event_date` は使わない）。

`posting_events`（ポスティングイベント）は期間バケット（例:「2026年1月〜」）であり、来場イベントではないため対象外。

### 登録元（アトリビューション）

| テーブル/フィールド | 内容 | BQへの到達可否 |
|---|---|---|
| `user_campaign_attribution(user_id, campaign_code, created_at)` | `?cv=コード` 経由の登録。用途例: 全国キャラバンの会場別QR | ◯ publicパイプラインで到達済み |
| `auth.users.raw_user_meta_data`（jsonb） | `provider`（line/email）, `line_user_id`, `line_official_account_friend` | **✕ publicパイプライン未到達**（プライベート版のみ） |
| `user_referral(user_id, referral_code)` | 自分の紹介コード（誰が自分を紹介したかではない） | - |

紹介者→被紹介者の関係は、直接のカラムでは保存されていない。紹介ミッション達成時に紹介者へ付与される `achievements`/`xp_transactions` の記録からしか間接的に追えない（**今回はスコープ外・別途検討事項として記録するに留める**）。

### 既存のBigQueryパイプライン

| Publication / Slot | 対象 | 用途 |
|---|---|---|
| `bq_pub` / `bq_slot` | 全スキーマ（`auth`含む） | プライベート版。`auth.users`の生JSONBメタデータも含む |
| `bq_pub_for_all` / `bq_slot_for_all` | `public`スキーマのみ | 社内公開版。`FOR TABLES IN SCHEMA public` なので、**新しくpublicスキーマにテーブルを追加するだけで自動的に配信対象になる**（`user_emails`の実績あり） |

`public.user_emails` は `auth.users.email` を publicスキーマへミラーする実装（トリガー同期・RLS有効・ポリシーなしでアプリからは不可視）がすでにある。これと同じパターンを登録経路フィールドにも使う。

## 決定事項

1. **集計・分析の置き場所**: 両方。まずBQ基盤側のギャップを埋める。管理画面ダッシュボードは将来検討。
2. **LINE登録経路のpublicパイプライン対応**: 必要。登録経路別（LINE/メール/キャンペーン）の分析をしたいため、`user_emails` と同じミラーパターンで対応する。
3. **GEO_CHECKINの扱い**: イベント集計に含める。`chore/hamadori-phase1-cleanup` の `develop` マージを待つ。

## 対応方針

### Step 1（実装済み）: 登録経路ミラーテーブルの追加

`public.user_emails` と同じ設計で、登録経路フィールドをミラーする。`line_user_id` は要検討事項のとおりPIIに近いため含めず、`provider`/`line_official_account_friend` のみをミラーする（`supabase/migrations/`内の対応マイグレーション参照）。

- 新テーブル案: `public.user_registration_channels`
  - `id uuid primary key references auth.users(id) on delete cascade`
  - `provider text`（`line` / `email` など。`raw_user_meta_data->>'provider'`）
  - `line_official_account_friend boolean`（`raw_user_meta_data->>'line_official_account_friend'`。友だち状態は事後に変わるため、`line_user_id`のようなPIIに近い値そのものは複製しない方針で検討）
  - `created_at`, `updated_at`
- `auth.users` への `INSERT OR UPDATE OF raw_user_meta_data` トリガーで同期（`sync_user_email()` と同じ `SECURITY DEFINER` + `search_path = ''` パターン）
- RLS有効・ポリシーなしでアプリから不可視、`bq_user` へ `SELECT` 付与
- `bq_pub_for_all` は `FOR TABLES IN SCHEMA public` のため、追加のpublication変更は不要（自動的に配信対象になる）
- **要検討**: `line_user_id` 自体を含めるかどうか。含めない場合、LINE経由ユーザーの名寄せ（同一人物の複数チャネル紐付け等）はできない。分析要件次第で判断する。

### Step 2（着手可能・GEO_CHECKINは`main`にマージ済み）: イベント参加のBQ側集計モデル

BQ側で以下のようなビュー/dbtモデルを定義する。

```sql
-- イベント参加ログ（1行 = 1ユーザーの1イベント来場）
with event_visits as (
  select
    a.user_id,
    a.mission_id,
    m.title as event_title,
    date(a.created_at) as visit_date,
    a.created_at as visited_at
  from achievements a
  join missions m on m.id = a.mission_id
  where m.required_artifact_type in ('QR', 'GEO_CHECKIN')
)
select * from event_visits
```

これをベースに:

- **登録元別のイベント参加数**: `event_visits` と `user_campaign_attribution` / `user_registration_channels` をJOIN → 登録元ごとに `count(distinct mission_id)` や `count(*)`
- **イベント→イベントの遷移**: `event_visits` を `user_id, visited_at` でソートし、`lag()`/`lead()` で「直前/直後に行ったイベント」を取り、`(event_title, next_event_title)` の組み合わせを集計
- **同日複数参加**: `visit_date` でグルーピングし、`count(distinct mission_id) > 1` のユーザー・日を抽出

### Step 3（将来検討）: 管理画面ダッシュボード

Step1・2が安定してから、`/admin` に上記集計のサマリ画面を追加するかどうかを別途検討する。BQ側のビューをそのままSupabase側で再実装するのは二重管理になるため、BQ→Supabaseへの結果書き戻し、もしくはBQを直接叩くBIツール（Looker Studio等）の採用も選択肢に入れる。
